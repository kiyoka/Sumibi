# Decisions API / Jev 全件比較サマリー

## 結論

**今回の質問文v2・入力データでは、Jevを継続するのが妥当です。Decisions APIへの置き換えは現時点では見送ります。** 英語入力の抑制は両者とも良好ですが、Decisionsは日本語の好ましい区切りの見逃しが多く、今回の測定では応答時間と参考費用にも優位性がありませんでした。

これは同時期の直接対決ではなく、今回のDecisions実測と保存済みJev実測の比較です。API全体の性能や、プロンプト調整後の結果を断定するものではありません。

## 共通閾値0.8での比較

47例・1239打鍵のうち、両者とも1207打鍵をAPIで測定し、shell/gpgの32打鍵をローカル除外しました。

| 項目 | Decisions (`gpt-6-luna`) | Jev (`jev-1.13.0`・過去測定) |
|---|---:|---:|
| 好ましい28位置の検出 | 12（42.9%） | 25（89.3%） |
| 許容できる早期発動 | 9 | 8 |
| 待つべき位置での発動 | 16 | 10 |
| 英語15例・685打鍵の発動 | 0 | 0 |
| 応答時間 p50 / p95 | 301.0 / 435.5 ms | 229.4 / 359.0 ms |
| p99 | 694.5 ms | 未保存 |
| 概算費用・1000打鍵 | $0.035957 | $0.020933 |
| 全件の概算費用 | $0.044551 | $0.025936 |

Decisionsは445510入力トークン。途中のタイムアウト1件を明示的に再送し、合計1208試行となりました。遅延集計には失敗試行も含みます。その1件の使用量は不明なので費用は判明分のみで、請求総額ではありません。漢字変換APIの費用は含みません。

## 閾値だけで改善できるか

Decisionsの閾値を0.6に下げると好ましい位置を27/28検出しますが、待つべき発動が30件に増えます。0.9では好ましい位置の検出が2/28まで減ります。Jevは0.9で19/28を検出し、待つべき発動0件でした。共通の0.8が両モデルで同じ校正を持つわけではありませんが、今回の範囲では単純な閾値変更だけで置き換えを支持できません。

devのみで「待つべき発動最小」を優先すると両者とも0.9が選ばれました。評価側21位置の検出はDecisions 1件・Jev 14件、待つべき発動はDecisions 4件・Jev 0件です。この保守的な選択を実用推奨値とはせず、従来のJev設定は変更しません。

## 代表例

- `arigatou␣gozaimasu␣`：両者とも最初の空白と最後の空白で閾値0.8を超えました。最初は許容、最後は好ましい位置です。
- Decisionsは `ask_repeat` の好ましい位置が0.79、`read_book` が0.75、`use_pen` が0.78で見送りました。
- 日本語の半角・全角コンマ後でも閾値0.8未満の見逃しがありました。低頻度の `!` だけの問題ではありません。
- 英語長文を含む全685打鍵では、両APIとも閾値0.8で発動しませんでした。
